# Agent 按序转发修复（2026-09-11）

## 问题与复现

源码基线 `92e2a97`（v2.26.1 后的文档提交）。Agent 在上游 TCP connect 期间持有请求锁，每个 DATA 分别异步申请同名锁；锁等待者不保证 FIFO，不能作为字节流顺序保证。

使用已部署 2.26.1 Agent 类、真实 Vertx 与 loopback TCP 的隔离程序，顺序调用 CONNECT 和 8 个 DATA，输入 0..7 在 30 次中均变为 7..0；未人为增加延迟或锁。单独编译基线源码后同样 30/30 失败。此场景解释了 HTTP 正文在请求头之前到达、multipart 边界被解析成 method 的现象，但测试比率不是现场故障率。

## 修复边界

仅改变 Agent 内部请求转发与资源生命周期，保持 Server/Agent 协议、鉴权和配置兼容。CONNECT 立即注册请求；每个请求在同一 Vertx context 中拥有 FIFO，串行完成上游写入。关闭、失败和 session 替换清理该请求；异步回调核验请求身份和来源 session，不能复活旧请求或写入新 session。Agent 复用 TCP/WebSocket client，停止时取消周期任务、关闭 client，并拒绝迟到的控制连接。

每请求待发送数据（含当前未完成写入）上限 1 MiB。它不是文件总大小限制；慢上游导致积压超过上限时明确关闭该请求并通知 Server。没有通过无限缓存、丢弃部分 DATA 或全局暂停共享通道掩盖问题。当前限制是局部容量保护，不构成完整的端到端流控；未来若要无损承受长时间慢上游，应设计协议级窗口及全局容量治理，不能简单放大队列。
